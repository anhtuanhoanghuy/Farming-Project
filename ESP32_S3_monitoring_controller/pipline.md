## Blocking Decisions

Resolve these before locking public interfaces or implementing dependent modules:

1. **Sensor decoding:** supplied DO/pH transmitter manuals define the register maps and measurement limits; firmware and `requirement_sensor.md` now enforce DO saturation `0–200%` and pH temperature `0–60°C`. Hardware still needs to confirm the configured baud/address, selected Modbus function, byte/word order, scale, and live values.
2. **Four-load safety acceptance:** schematic confirms GPIO39–42, active-HIGH ON/LOW OFF. Confirm that LOW is safe for each real actuator before energizing board outputs; all current code defaults LOW.
3. **Network policy:** Requirements give conflicting 2-second/5-second ping intervals, sub-1-second/10-second Ethernet decisions, and a <5-second acceptance target. Define detection, switching, failback, and whether the target includes MQTT recovery.
4. **Safety policy:** `requirement_mqtt.md` D-07 defines the timeout from continuous loss of the MQTT control channel; P5 must implement and verify start/reset behavior and non-restoring recovery.
5. **BLE lifecycle/security:** BLE is limited to initial/runtime provisioning; operational control/config/status uses MQTT. Broker ACL and per-device authorization remain production-security work.
6. **Security scope:** The product has no OTA; firmware is updated over USB. Define signing/key custody, recovery, and USB/JTAG policy before production security work. eFuse activation is irreversible.
7. **Hardware/build baseline:** MCU module is ESP32-S3-WROOM-1U. W5500, relay, LED, and reset mappings are recorded; RS485 UART1 GPIO17/18 and DE/RE GPIO8 in `main/app_pins.h` remain provisional until checked against the board schematic/revision. Flash size and component versions also need confirmation.
8. **Load sensor-rule policy (superseded 2026-10-16):** weekly schedule and sensor-triggered ON/OFF conditions may be enabled together per load. Sensor rules outrank schedules; OFF wins if both sensor rules match one sample. Sensor rules use `v1` from a valid sample and stable IDs `sensor_001`…`sensor_005`. See `requirement_loads.md` §§5.2, 6.8.

## Deferred Work: P6 Network Closure

Do not start this work until P7 MQTT is configured and verified against the intended broker and a real ESP32-S3/W5500 device plus Wi-Fi network are available. The current source builds, but build success is not evidence of reliable failover.

1. **Confirm WAN probe suitability:** ICMP to either configured public target is the current required WAN check. Before acceptance, test on the deployment network that ICMP is allowed and at least one target is reachable. If ICMP is blocked by policy, pause acceptance and decide on an independent WAN probe; do not use MQTT-broker reachability as the fallback or trigger failover for broker-only outages.
2. **Harden probe lifecycle:** check and handle every `esp_ping_start()` result; clean up all created sessions on partial-start/error paths; bound probe completion/recovery; and verify late callbacks cannot access a reused probe job. Source now handles start errors, rejects an all-target start failure, checks session deletion, stops an over-time probe after 15 s, and restarts if stop completion is not reported within a further 3 s rather than reusing a live job. Confirm these paths with fault injection where feasible.
3. **Make interface switching failure-safe:** check `esp_netif_set_default_netif()` and verify the resulting default netif; verify the global DNS update (the LwIP setter has no return value); restore the previous route/DNS on failure. Source now performs these checks and only notifies MQTT to restart after a consistent switch or successful rollback. Exercise rollback/failure paths on target.
4. **Run network hardware acceptance:** exercise AC-01–AC-06, AC-12–AC-15, and AC-17 from `technical_requirements_network_failover_FINAL.md` (including link loss, silent WAN loss, failback hysteresis, broker-only outage, W5500 recovery, same-subnet routing, 100-cycle memory check, and 24-hour soak). Record actual timing from link/WAN failure through MQTT resubscription, reconnect/backoff behavior, heap/session counts, and pass/fail evidence here.
5. **Recheck resource headroom:** inspect the successful ESP32-S3 build's static IRAM report (currently 16,383/16,384 bytes used; 1 byte free), task stack high-water marks, and watchdog behavior before sign-off.

## Deferred Work: P4 Sensor Datasheet Verification

The DO saturation and pH temperature range checks are updated in firmware and `requirement_sensor.md`. Complete the following validation before closing P4:

1. **Confirm sensor communication settings:** inspect each DO/pH transmitter on the board and record its Modbus address and baud rate. Both manuals specify factory-default 4800 baud, while firmware currently uses 9600 baud; configure one side consistently before polling.
2. **Run protocol unit tests and build:** execute `app_modbus_proto_test` on a host with a C runtime, including DO saturation at 200% and rejection above 200%, and pH temperature at 0/60°C and rejection outside the range. The ESP32-S3 build passed on 2026-10-13 for the current source; rerun and record the result if further code changes are made.
3. **Verify live sensor readings on hardware:** capture raw Modbus registers and decoded DO/pH values, confirm address/function/byte-word order/scaling against the manuals, and test disconnection of each sensor independently to ensure the other continues reporting.
4. **Record acceptance evidence:** update P4 status and this work log with board revision, sensor settings, test commands/results, sample readings, fault-isolation results, and any remaining mismatch. Do not mark P4 complete until these checks pass.

## Working Rules

- Implement one phase at a time; do not mark a phase complete until its completion gate has evidence.
- Keep module APIs and shared data types in sync with this file and the source requirements.
- **Before each task/session:** update `Active Work` with phase, module, task, owner, and known blockers before editing or running tests.
- **After every meaningful action:** update the module/phase status and append the result (files changed, command/test and outcome, decision, or blocker) to `Work Log` before starting the next action. Do not batch several completed tasks and backfill progress later.
- **At handoff or pause:** clear or mark `Active Work` as paused/completed and record the exact next action so another agent can continue without asking for status.
- Never enable irreversible production eFuse settings on a development/production unit without an approved key, recovery, and authorization procedure.

## Decisions

- Provisioning sessions (first-time and runtime) always allow `wifi-scan` because the app has no manual SSID entry: runtime provisioning switches the Wi-Fi radio on (`app_network_wifi_radio_on()`) even in Ethernet-only mode and restores it at the end (`app_network_wifi_radio_restore()`). Runtime provisioning now disconnects the active Wi-Fi briefly to test new credentials; MQTT may reconnect, and the old credentials are restored if the test fails.
- Button handling lives in `app_sysmon` (not `app_nvm`); factory reset uses a two-stage gesture (hold ≥5 s and release → runtime BLE provisioning if no re-press within 2 s; re-press within 2 s and hold 5 s → reset executes immediately, no release needed; 2 Hz LED at first 5 s, 10 Hz during reset; quick double-click toggles app logging; a button held at power-up is ignored until released); on execution it requests all outputs LOW through the interlock event, erases NVS, and restarts. `app_control` is the only relay GPIO owner. Schematic: user button SW3 = GPIO4 (R62 pull-up), LED_ERROR = GPIO38, LED_WIFI = GPIO36, LED_ETH = GPIO37 (IO36/IO37 are octal-PSRAM pins on the N8R8 module: PSRAM must stay disabled while these LEDs are used), no dedicated load LED.
- Provisioning policy: one valid config per BLE session; save only when a network came up (Wi-Fi OK, Ethernet OK, or Wi-Fi failed with Ethernet up -> WARNING); no network -> not saved, BLE stops after the result is read, controller restarts into provisioning; validation errors keep the session open. Wi-Fi failure reasons reported: wrong_password, ap_not_found, unknown. WAN (internet) validation of the new Wi-Fi is not part of this step.
- MQTT identity: broker URI/credentials come from Kconfig; development default is public `mqtt://broker.emqx.io:1883` (plaintext only, development); `user_id` from NVM; `device_id` = the ESP32-S3's own Wi-Fi STA MAC (`esp_read_mac(..., ESP_MAC_WIFI_STA)`) as 12 lowercase hex digits, not the phone or Bluetooth MAC; client id = device_id. Production requires a private TLS broker/per-device credentials. Safety interlock timeout is defined as loss of MQTT control channel; its expiry now delegates to `app_control`, which exclusively owns relay GPIOs.
- MQTT development broker: `mqtt://broker.emqx.io:1883`, public, unauthenticated plaintext; development only, never use for real/private control. Production must configure a private TLS broker with per-device credentials. Broker URI and credentials remain Kconfig-only, not BLE/NVS.
- `esp_netif_set_priority()` does not exist in ESP-IDF 5.2.6. Route priority is fixed at netif creation (ETH 120, Wi-Fi STA 100 default); `net_mgmt_task` additionally owns the default netif via `esp_netif_set_default_netif()`, which disables the automatic priority-based selection.
- Schematic pins: W5500 SCLK=GPIO12, MOSI=GPIO11, MISO=GPIO13, CS=GPIO10, INT=GPIO9. Relay DO0–DO3 = GPIO39–42, active HIGH/LOW safe. User button GPIO4; LED_ERROR/WIFI/ETH = GPIO38/36/37. RS485 UART/DE-RE pins in `app_pins.h` remain provisional and need schematic-confirmed allocation.
- W5500 recovery order follows FINAL spec 3.8: `esp_eth_stop` -> RST pulse (if wired) -> uninstall -> re-init SPI -> install -> `esp_eth_start`.
- Network timing follows `technical_requirements_network_failover_FINAL.md`; WAN probes run every 1 s and Wi-Fi reconnect uses full jitter, base 1 s, max 5 s, floor 200 ms.
- Sensor capacity: 4 RS485 interfaces plus 1 analog 4-20 mA sensor interface; known RS485 sensor types include SHT40, dissolved oxygen, and pH. NVM config arrays use these capacities with zero-based interface indices; analog conversion and generic runtime sample payload remain open.
- MCU module: ESP32-S3-WROOM-1U.
- Sensor registers: SHT40 input registers `0x0001` (temperature) and `0x0002` (humidity); DO concentration registers `0x0002-0x0003`, big-endian float; pH register `0x0000`, unsigned 16-bit value divided by 100.
- Actuators: four relay outputs; `app_config_t.load_name[4]` replaces the single `load_1_name` (provisional, pending load-model decision).
- GPIO/interface capacities: 4 DI and 4 DO; `APP_LOAD_COUNT` aliases the four DO channels. Central constants are in `main/defines.h`.
- Provisioning accepts only `ssid`, `password`, `user_id`, and `only_use_ethernet`. NVM persists those values, sensor configuration, and per-load control/schedule policy; broker source is Kconfig-only.
- BLE provisioning: after a successful save the device waits 2 s, stops BLE, and connects without rebooting. `prov-config` and `prov-status` return the ESP32-S3's own Wi-Fi STA MAC as lowercase `device_id` (not the phone or Bluetooth MAC), matching MQTT identity; the mobile app/backend must upsert the device only after `saved=true` and must not store Wi-Fi credentials. PoP is a provisional shared value (`APP_BLE_PROV_POP`).
